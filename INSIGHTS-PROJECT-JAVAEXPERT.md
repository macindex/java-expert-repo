Ecossistema Java Avançado & Arquitetura (Java 17+, Spring & JPA)🚨 Cenário de Entrevista: O Gargalo Invisível no Pool de Conexões"Temos um microsserviço Spring Boot em Java 17 com Spring Data JPA que atende a uma API de checkout de carrinho de compras. Durante picos de tráfego, o uso de CPU do microsserviço permanece baixo (menos de 20%), mas o tempo de resposta da API passa de 200ms para mais de 15 segundos, gerando timeouts em cascata. O pool de conexões do HikariCP fica completamente esgotado. Como você diagnosticaria e resolveria isso?"O que o entrevistador quer avaliar:Sua capacidade de identificar o problema clássico de $N+1$ queries, retenção desnecessária de conexões sob transações longas e seu conhecimento sobre a evolução do runtime do Java (Virtual Threads).Direcionamento da Resposta do Expert:Diagnóstico Inicial: Explicar que baixo uso de CPU combinado com esgotamento de threads/pool indica um gargalo de I/O ou contenção de locks, possivelmente causado por queries ineficientes que retêm conexões por muito tempo. Identificar a necessidade de inspecionar os logs para mitigar o efeito $N+1$ (onde o Hibernate faz uma consulta principal e dispara dezenas de consultas filhas de forma preguiçosa).Solução com JPA: Demonstrar o uso de JOIN FETCH na query JPQL ou a definição de um EntityGraph dinâmico para trazer os dados correlacionados em uma única viagem ao banco de dados.Otimização de Transação: Avaliar se o escopo do @Transactional está cobrindo chamadas externas de I/O (como requisições HTTP para APIs de terceiros). O correto é reduzir a transação apenas para a persistência para devolver a conexão ao pool o quanto antes.A Evolução com Java 21+: Mencionar que se a aplicação puder ser migrada para o Java 21, o uso de Virtual Threads (Project Loom) resolveria o esgotamento do pool de threads do servidor de aplicação (Tomcat), permitindo que milhares de requisições concorrentes aguardem o retorno do banco sem bloquear threads caras do Sistema Operacional.2. Microsserviços, APIs RESTful & Poliglotismo de Dados🚨 Cenário de Entrevista: A Degradação Oculta por Paginação"Nossa API de histórico de transações financeiras utiliza Postgres e paginação tradicional via LIMIT e OFFSET. À medida que um cliente antigo com milhões de transações clica nas páginas mais distantes do extrato (ex: página 5000), a query demora segundos para responder, degradando o banco de dados. Como redesenhar essa paginação mantendo a API performática?"O que o entrevistador quer avaliar:Seu conhecimento sobre o comportamento interno de indexação de bancos de dados relacionais e estratégias eficientes de paginação em grandes volumes de dados.Direcionamento da Resposta do Expert:Explicação do Problema: Explicar que a cláusula OFFSET 500000 LIMIT 100 obriga o Postgres a ler em disco e descartar as primeiras 500.000 linhas da tabela antes de retornar as 100 desejadas, invalidando os ganhos de performance do índice B-Tree.Solução Arquitetural (Keyset Pagination): Propor a transição para Paginação Baseada em Cursor (Keyset Pagination). Em vez de enviar o número da página, a API passa a receber o ID (ou o timestamp) do último registro da página anterior como parâmetro na URL:
WHERE transaction_date < :last_date_seen ORDER BY transaction_date DESC LIMIT 100.
Isso permite que o banco vá direto ao ponto no índice B-Tree de forma instantânea $O(\log N)$.Estratégia NoSQL (Poliglotismo de Dados): Para um cenário Expert (como o Inter Pag), propor mover dados históricos e imutáveis (transações com mais de 90 dias) para o DynamoDB. Explicar que usando o Single-Table Design do DynamoDB com PK: CLIENT_ID e SK: TRANSACTION_TIMESTAMP, a consulta paginada utilizando o token nativo (ExclusiveStartKey) mantém a performance perfeitamente constante e previsível, não importando o volume dos dados.3. Mensageria, Sistemas de Eventos e Observabilidade🚨 Cenário de Entrevista: O Mistério da Duplicação e Perda de Rastreabilidade"Implementamos um fluxo assíncrono onde o serviço de Originação de Crédito publica uma mensagem no Apache Kafka para o serviço de Notificação enviar um SMS ao cliente. Notamos dois problemas graves: em momentos de instabilidade na rede, alguns clientes recebem o SMS duplicado e, quando o SMS falha, o time de atendimento não consegue correlacionar o log do serviço de Notificação com a transação original que começou na Originação. Como você resolve a duplicidade e a falta de rastreabilidade?"O que o entrevistador quer avaliar:Domínio sobre as garantias de entrega de brokers de mensageria (Kafka), implementação de consumidores idempotentes e configuração de telemetria distribuída.Direcionamento da Resposta do Expert:Resolução da Duplicidade (Idempotência): Explicar que em sistemas distribuídos, a semântica padrão costuma ser At-least-once. Para evitar o processamento duplicado no destino, é mandatório implementar a idempotência na camada da aplicação (Consumidor Idempotente). O serviço de Notificação deve salvar o ID único da transação (ou uma chave de idempotência financeira) no Redis ou banco relacional antes de processar. Se a chave já existir, o evento é descartado com sucesso sem reprocessamento.Rastreabilidade com Distributed Tracing: Propor a implementação do OpenTelemetry. Ao publicar uma mensagem no Kafka, o cabeçalho (headers) do registro deve receber a propagação do contexto W3C Trace Context (contendo o TraceId e SpanId originais da requisição HTTP inicial).Visualização na Telemetria: Com isso, o consumidor extrai esse contexto dos headers do Kafka ao ler a mensagem e continua o trace nos logs subsequentes. Isso permite buscar o TraceId único diretamente no Grafana/New Relic e enxergar a linha do tempo completa do evento cruzando a barreira dos microsserviços.4. Engenharia de Qualidade, Nuvem (AWS) & DevOps🚨 Cenário de Entrevista: O Deploy Assassino de Conexões no Kubernetes"Temos um microsserviço Spring Boot crítico rodando na AWS dentro de um cluster EKS. Segurança e o Diferencial de Negócio: Adquirência🚨 Cenário de Entrevista: A Falha Parcial na Captura e Liquidação de Pagamentos"Em um fluxo de adquirência (como o da Inter Pag), o cliente realiza uma compra em um e-commerce. O nosso Serviço de Captura aprova a transação com sucesso junto à bandeira do cartão e emite a confirmação na tela para o usuário. No entanto, o passo seguinte — que é enviar a transação para o Serviço de Liquidação (para o lojista receber o dinheiro futuramente) — falha de forma irrecuperável por esgotamento de memória (OOM). O banco de dados do Serviço de Captura está inconsistente com o da Liquidação. Como você desenharia essa transação distribuída de forma resiliente e em conformidade com o PCI-DSS?"O que o entrevistador quer avaliar:Seu conhecimento em transações financeiras distribuídas (Padrão Saga), resiliência em sistemas assíncronos críticos e conformidade técnica setorial (PCI-DSS) para tratamento de dados de cartão.Direcionamento da Resposta do Expert:Abordagem Arquitetural (Padrão Saga): Explicar que o uso de transações ACID tradicionais distribuídas de duas fases (2PC) causaria travamento de recursos em alta escala. A resposta correta exige a adoção do Padrão Saga Coreografado ou Orquestrado com ações de compensação.Implementação da Solução Prática:O Serviço de Captura processa o pagamento e persiste o registro no banco local através do padrão Transactional Outbox, garantindo que o evento de captura seja salvo na mesma transação atômica do negócio.Um worker (como o Debezium ou uma thread interna) lê a tabela Outbox e publica o evento PaymentCapturedEvent no Kafka.O Serviço de Liquidação consome o evento. Caso ele falhe após tentativas automáticas de Retry com Backoff Exponencial e Jitter, o erro é capturado de forma definitiva.O ecossistema emite um evento de falha (LiquidationFailedEvent), consumido de volta pelo Serviço de Captura, que imediatamente dispara uma ação de compensação técnica para estornar (Void) o valor capturado na bandeira, mantendo a consistência eventual do saldo.Conformidade PCI-DSS: Adicionar que em nenhuma das etapas os dados sensíveis do cartão de crédito (como o PAN ou CVV) podem transitar abertamente nos tópicos do Kafka ou serem armazenados em texto claro nos bancos de dados. Deve-se arquitetar um serviço isolado de Tokenização sob uma sub-rede ultra restrita que converte o número do cartão em um Token seguro no momento da entrada. Apenas o token seguro circula entre as Sagas de Captura e Liquidação, mitigando riscos de segurança e potenciais multas regulatórias milionárias.💡 Dica de Postura e Soft Skills para a Entrevista:Ao responder a estes cenários, demonstre de forma intencional o seu Sentimento de Dono (Ownership). Em vez de dizer apenas "eu escreveria o código do Kafka", fale como um Expert: "eu analisaria as métricas de lag de consumo no Grafana, entenderia o impacto financeiro de um evento duplicado para o negócio da Inter Pag e proporia o modelo arquitetural que gerasse a maior resiliência com o menor custo operacional".
